# 宿データの追加・修正

## このスキルが必要な理由

宿を1軒足すという作業は、実際には**5つのファイルと1つの品質基準にまたがる**。
`data.js` に足しただけで終わらせると、静的APIと軒数表記とLPが食い違い、
サイトの売りである「情報の正直さ」が崩れる。

さらにこのサイトの掲載基準は「ユニットバスの部屋は一室も載せない」という強い約束で成り立っている。
公式サイトの写真や紹介文は**セパレートに見えるように書かれていることが多い**ため、
「セパレートである証拠」を集めるだけでは足りず、**「ユニットバスである証拠」を能動的に探して
見つからないことを確認する**必要がある。これを反証チェックと呼び、過去のコミットでも
「調査+反証チェック済み」として品質の根拠にしている。

## 手順

### 1. 掲載できるか判定する

掲載できるのは次のいずれか。どれにも当てはまらない宿は**載せない**という判断が正しい。

| ケース | 表現方法 |
| --- | --- |
| 全客室が風呂・トイレ別（洗い場付き） | `sepScope` を付けない（既定） |
| 一部の客室タイプのみ風呂・トイレ別 | `sepScope: "partial"` を付け、**セパレートを確認できた客室タイプだけ** `rooms[]` に載せる |
| 客室に浴室が無く、入浴は大浴場・外湯（城崎の外湯文化など） | `rooms[].bath.type` に「浴室なし」を含める。派生フラグ `noRoomBath` / `someNoRoomBath` が自動で立つ |

3点ユニットバスしかない宿は、他がどれだけ魅力的でも対象外。

### 2. 一次情報で調査する

公式サイトを最優先し、大手予約サイト（楽天トラベル・一休など）と自治体・観光協会の情報で裏を取る。
確認したURLはすべて `sources[]` に残す。ここが後から検証できるかどうかを決める。

公式サイトへ直接アクセスできないことがある（プロキシ制限）。その場合は検索エンジン経由の
スニペットで確認し、**その事実を `uncertain` に書く**。「確認できなかった」と正直に書くほうが、
確認したふりをするより価値が高い。

集める情報は `references/data-schema.md` に全フィールドを載せている。作業前に読むこと。

### 3. 反証チェックを行う

各宿について、**ユニットバスの証拠を探す**つもりで検索する。有効な切り口:

- 「<宿名> ユニットバス」「<宿名> 洗い場」で口コミを探す
- 客室写真の浴室が便器と同室に写っていないか
- 「バス・トイレ別」を謳っているのが**特定の客室タイプだけ**でないか（→ `sepScope: "partial"`）
- 「洗い場付き」と書かれているのが大浴場のことで、客室浴室はシャワーブースではないか

反証が見つかったら、掲載を諦めるか `sepScope: "partial"` に切り替えるか、`rooms[]` を絞る。
見つからなかった場合も、**どこまで確認してどこが未確認か**を `uncertain` に書く。

### 4. 調査記録を `docs/hotel-research.json` に残す

`data.js` の `sources` / `uncertain` の裏付けとなる調査の全記録。宿ごとに
`hotel` オブジェクトと、確認した内容・反証チェックの結果を書く。
既存レコードと同じ形に揃えれば十分。

### 5. `assets/js/data.js` の `HOTELS` に追加する

`references/data-schema.md` のフィールド定義に従う。既存レコードをコピーして埋めるのが早い。

料金の意味が宿タイプで違う点に注意（ファイル冒頭のコメントにも書かれている）:

- `type: "onsen"` → 1泊2食・2名1室の**1名あたり**参考料金
- `type: "business"` → 素泊まり・1名の参考料金

`hasFreeKashikiri` / `noRoomBath` / `someNoRoomBath` / `minPrice` は
ファイル末尾の `forEach` が実行時に計算する**派生フラグなので、手で書かない**。

### 6. 派生ファイルを更新する

ここが一番抜けやすい。順番に実行する。

```bash
# 静的API（api/hotels.json）を data.js から再生成
node .claude/skills/add-hotels/scripts/gen-hotels-json.js

# 追加した宿が属するエリアのLPを再生成（sitemap.xml 全体も一緒に更新される）
node tools/gen-area-lp.js osaka        # tokyo | osaka | kyoto | okinawa | hokkaido
```

- **`api/hotels.json` は手で編集しない。** 以前は手作業だったため、`data.js` に派生フラグが増えても
  JSON側は古いまま、という形で実際にズレていた。スクリプトなら data.js を読んで書き出すのでズレない。
  実行後に「[要確認]」の警告が出たら、`sources` や `bath.type` の抜けを直す。
- **LPは軒数をタイトルに埋め込んでいる**（`{N}選`）。宿を足したら該当エリアのLPを必ず再生成する。
  複数エリアにまたがって足したなら、**エリアごとに1回ずつ**実行する。
- OGP画像も軒数を表示しているので、必要なら `node tools/gen-ogp.js`（詳しくは area-lp スキル）。

### 7. README の軒数を更新する

README の「掲載データについて(実在施設)」に、総数と内訳（エリア別軒数）が書かれている。
利用者向けの説明として手厚く維持されているので、数字が合わなくなったら直す。
実際に README は履歴上15回更新されている。

### 8. 目視で確認する

```bash
python3 -m http.server 8000
```

- トップと検索結果に出るか、エリア絞り込みで拾えるか
- 詳細ページ（`detail.html?id=<id>`）で客室表・貸切風呂・出典が正しく出るか
- `sepScope: "partial"` なら「一部客室 風呂・トイレ別」と表示されるか
- 再生成したLP（例 `osaka.html`）に新しい宿が載り、軒数が更新されているか
